## D-001 재고 불일치를 모델에 담는 범위

- **상태:** 결정

**배경**
매장 근무 경험상 전산 재고는 입고·판매·온라인 출고 시 정확히 갱신되었다. 불일치는 전산에 기록되지 않는 실물 사건(도난, 고객의 제품 위치 이동, 픽업 주문 취소 후 미처리)에서 발생했다.

**선택지**
| 선택지 | 내용 | 검토 결과 |
|---|---|---|
| A | 실사조정 이력과 조정 사유 관리 | 현업 시스템에 이미 존재하는 기능 |
| B | 재고를 상태별로 구분 (가용, 주문보관 등) | 현업에서 겪은 공백을 직접 해결 |
| C | 진열 위치 관리 | 현업 시스템에 이미 존재, 범위 대비 부담 큼 |

**판단 근거**
A와 C는 현업에 이미 있어 경험 기반 보완점이 아니다. 반면 픽업 주문이 포장완료 후 취소되면 전산 재고는 복원되지만 실물은 봉투에 남아 있는 공백은 기존 구조에서 보이지 않았다.

**결정**
B를 차별 요소로 채택한다. A는 재고 계산을 위한 기본 구조(실사조정 변동유형)로만 포함하고, C는 향후 확장으로 남긴다.

**영향 산출물:** 논리 ERD(매장재고, 재고변동이력), 표준 사전(재고상태코드, 변동유형코드)

## D-002 매장재고 구조

- **상태:** 결정

**선택지**
| 선택지 | 장점 | 단점 |
|---|---|---|
| ① 컬럼 방식 (가용수량, 주문보관수량, 테스터수량 컬럼) | 한 행에서 바로 조회 | 상태 추가 시 컬럼 추가 필요, 변동이력과 대응시키기 번거로움 |
| ② 행 방식 (매장, SKU, 재고상태코드, 수량) | 상태 추가 시 코드값만 추가, 변동이력과 같은 구조 | 실재고 조회 시 합계 필요 |

**판단 근거**
재고변동이력에도 재고상태코드를 두면 "매장재고 수량 = 재고변동이력 누적 합계" 점검을 매장·SKU·상태 단위로 그대로 수행할 수 있다. 상태 간 이동(가용 → 주문보관)도 두 행의 변동으로 자연스럽게 표현된다.

**결정**
② 행 방식. PK는 (매장ID, SKU_ID, 재고상태코드). 재고상태코드 값은 `가용`, `주문보관`, `테스터`이다 (D-006에 따라 재진열대기는 두지 않음).

**영향 산출물:** 논리 ERD(매장재고), 품질 점검 SQL

## D-003 테스터재고 포함 여부

- **상태:** 결정

**배경**
근무 매장의 실재고는 가용재고와 테스터재고의 합으로 관리되었다. 테스터는 뷰티 리테일 특유의 재고 상태이다.

**선택지**
① 제외 ② 재고상태로 포함, 가상 데이터 최소화 ③ 전면 포함

**판단 근거**
테스터는 뷰티 리테일의 현실성을 보여주지만, 이 프로젝트의 핵심은 주문보관 상태이다. 구조에는 포함하되 데이터 생성 부담은 줄인다.

**결정**
② 재고상태코드에 `테스터`를 정의하고, 변동유형에 `테스터전환`, `테스터폐기`를 둔다. 가상 데이터는 소량만 생성한다.

**영향 산출물:** 표준 사전(코드값), 가상 데이터 생성

## D-004 매장 처리 상태 관리 단위

- **상태:** 결정

**배경**
픽업·매장 출고 주문은 접수 → 포장완료(고객에게 QR 발송) → 수령완료(QR 스캔) 순으로 처리된다. 영업 마감 후 취소된 경우 다음 날 봉투를 하나씩 확인해야 했다.

**선택지**
| 선택지 | 장점 | 단점 |
|---|---|---|
| ① 주문 단위 | 구조 단순, 봉투 1개 = 주문 1개 흐름과 일치 | 부분 취소 표현 불가 |
| ② 주문상세 단위 | 부분 취소 표현 가능 | 관리 대상 증가, 조회 복잡 |

**판단 근거**
근무 매장에서는 부분 취소가 불가능했고 포장·QR 발송·수령이 모두 주문 단위로 이루어졌다.

**결정**
① 주문 단위.

**가정·한계:** 부분 취소 불가를 전제로 한다. 부분 취소가 가능한 환경이라면 주문상세 단위로 변경해야 한다.

**영향 산출물:** 논리 ERD(주문), 표준 사전(처리상태코드)

## D-005 처리 상태 기록 방식

- **상태:** 결정

**선택지**
| 선택지 | 장점 | 단점 |
|---|---|---|
| ① 일시 컬럼 (포장완료일시, 수령완료일시, 취소일시) | 단순, 조회 쉬움 | 상태 추가 시 컬럼 추가 |
| ② 주문상태이력 테이블 | 상태 확장에 유연 | 테이블 추가, 조인 필요 |

**판단 근거**
원천(Olist) 주문도 승인일시, 택배 인계일시, 배송완료일시처럼 일시 컬럼 방식이다. 상태 흐름이 짧고 고정적이어서 이력 테이블의 유연성이 필요하지 않다.

**결정**
① 일시 컬럼 방식. 현재 상태는 주문상태코드로 별도 보관한다.

**영향 산출물:** 논리 ERD(주문), 매핑 정의서

## D-006 포장완료 후 취소된 재고의 처리와 표시

- **상태:** 결정 (변경 1회)

**배경**
픽업·매장 출고 주문이 포장완료 후 취소되면 전산 가용재고는 즉시 복원되지만 실물은 포장 봉투에 남는다. 취소 사실을 모르는 상태에서 고객이 해당 상품을 찾으면, 전산에는 재고 1개가 보이지만 진열대에 없어 찾는 데 오랜 시간이 걸렸다. 고객이 많은 시간대에는 한 고객의 상품을 찾는 데 긴 시간을 쓰기 어렵고, 고객도 기다려야 한다.

**초기 판단**
포장완료 후 취소된 재고를 `재진열대기` 상태로 두고, 재진열완료 처리 시 가용으로 복원하려 했다.

**변경 이유**
문제는 판매 가능 여부가 아니라 재고의 위치를 모르는 것이었다. 재진열 전 판매를 막는 것은 불필요한 판매 손실이고, 할인 행사 기간처럼 취소가 많을 때 건별 재진열완료 처리는 현장에 추가 부담을 준다.

**선택지**
| 선택지 | 장점 | 단점 |
|---|---|---|
| ① 재진열대기 상태 + 건별 재진열완료 처리 | 재고 위치 정확 | 판매 제한, 현장 처리 부담 |
| ② 가용 즉시 복원 + 주문 일시로 취소 봉투 확인 대상 조회 | 추가 작업 없음, 판매 지장 없음 | 재진열 여부는 알 수 없어 확인 안내 수준 |
| ③ ② + 매장 단위 일괄 정리 완료 기록 | 안내 정확도 향상 | 소량의 추가 작업 |

**판단 근거**
목표는 "전산 재고는 있는데 보이지 않는" 상황에서 직원이 취소 봉투부터 확인하도록 안내해 탐색 시간을 줄이는 것이다. 이미 기록되는 출고매장, 포장완료일시, 취소일시만으로 안내가 가능하므로 새로운 입력 절차를 만들지 않는다.

**결정**
② 취소 시 가용재고를 즉시 복원한다. 포장완료일시와 취소일시가 모두 있고 취소 후 2일 이내인 주문의 상품을 매장·상품별 "취소 봉투 확인 대상"으로 조회한다. 재고상태코드에 재진열대기를 두지 않고, 변동유형에 재진열완료를 두지 않는다.

**가정·한계**
재진열 여부를 기록하지 않으므로 이 조회는 "봉투에 있을 가능성이 있는 재고" 안내이며 확정 정보가 아니다. 정확도가 더 필요하면 ③으로 확장한다. 조회 범위 2일은 현장에서 다음 날까지 정리하던 관행에 근거한다.

**영향 산출물:** 논리 ERD(주문의 출고매장ID·포장완료일시·취소일시), 업무 SQL(취소 봉투 확인 대상 목록, 할인 행사 기간 포장완료 후 취소 건수)

## D-007 실사조정 사유 처리

- **상태:** 결정

**배경**
근무 매장에서는 제품이 보이지 않으면 온라인 주문 접수를 막기 위해 재고를 먼저 차감하고, 원인을 알 수 없어 `포스기 오류`를 기본값처럼 선택했다. 제품을 찾으면 다시 증가 조정했다. 이 경우 조정 사유 데이터가 실제 원인을 반영하지 못한다.

**선택지**
| 선택지 | 장점 | 단점 |
|---|---|---|
| ① 재조정 시에도 사유 선택 | 구현 단순 | 어떤 조정을 되돌린 것인지는 추정 필요 |
| ② 재조정이 원 조정을 참조 | 짝을 정확히 추적 | 현장 입력 절차 증가 |
| ③ 차감 시 `원인미상` 사유 허용 | 거짓 사유 감소 | 원인미상 누적 시 분석 가치 저하 |

**판단 근거**
입력 항목이 늘면 바쁜 현장에서 다시 기본값을 고르게 된다. 입력 부담을 늘리지 않으면서 사유 정확성을 높이는 방향을 택한다.

**결정**
③ + ①. 사유 코드에 `원인미상`과 `미발견후발견`을 추가한다. ②는 향후 확장으로 남긴다.

**영향 산출물:** 표준 사전(조정사유코드), 품질 점검 SQL

## D-008 조정 후 복원 판단 기준

- **상태:** 결정

**배경**
현장에서는 제품이 안 보이면 해당 시간대, 다음 근무 타임, 다음 날까지 찾아보고 없으면 도난이나 오류로 간주했다.

**결정**
차감 조정 후 2일 이내 같은 매장·SKU의 증가 조정을 "복원 건"으로 본다.

**판단 근거**
다음 날까지 탐색하던 현장 관행에 하루의 여유를 두었다.

**가정·한계:** 한 매장의 경험에 근거한 기준이다. 결과 수치는 가상 데이터에 기반하므로 발견이 아니라 점검 방법의 시연이다.

**영향 산출물:** 품질 점검 SQL, 가상 데이터 생성 규칙

## D-009 판매자 포함 여부

- **상태:** 결정 (변경 1회)

**확인한 사실**
- health_beauty 판매자 492명
- 원천은 여러 판매자가 입점한 마켓플레이스 구조

**초기 판단**
여러 브랜드를 취급하는 리테일이므로 판매자를 포함하려 했다.

**변경 이유**
브랜드(상품을 만든 주체, 상품의 속성)와 판매자(고객에게 파는 주체, 거래의 속성)를 혼동했음을 확인했다. 멀티브랜드 리테일은 브랜드는 여러 개여도 판매자는 자사 하나인 구조로 설정한다.

**선택지**
| 선택지 | 장점 | 단점 |
|---|---|---|

## D-011 회원 식별자

- **상태:** 결정

**확인한 사실**
- customers 99,441행, orders 99,441행으로 행 수가 같음
- customer_id 고유 수 99,441 / customer_unique_id 고유 수 96,096
- customer_id를 2개 이상 가진 사람 2,997명

**해석**
customer_id는 주문마다 새로 발급되는 주문용 고객 번호이다. 이를 회원 식별자로 쓰면 재구매 고객이 여러 회원으로 나뉘어 회원 수와 회원별 구매 이력이 왜곡된다.

**선택지**
| 선택지 | 장점 | 단점 |
|---|---|---|
| ① customer_id | 원천 그대로, 변환 불필요 | 동일인이 여러 회원으로 분리 |
| ② customer_unique_id | 실제 사람 단위 식별 | 주소 처리 추가 결정 필요 |

**판단 근거**
회원 엔터티는 실제 사람을 식별해야 한다. 2,997명의 분리는 재구매·회원 분석을 불가능하게 만든다.

**결정**
- customer_unique_id 기준으로 회원을 구성한다.
- 회원ID는 대체키(일련번호)로 생성하고, customer_unique_id는 원천회원번호 컬럼에 보관한다. 가상 매장 회원과 같은 식별 체계를 쓰기 위함이다.
- 주소: 주문에 배송지(우편번호·도시·주)를 보관하고, 회원에는 최근 주문 기준 주소를 둔다.

**영향 산출물:** 논리 ERD(회원, 주문), 매핑 정의서

## D-015 상품명·브랜드·SKU·정가 생성 방식

- **상태:** 결정

**확인한 사실**
원천 상품에는 상품명(이름 길이만 존재), 브랜드, 옵션, 정가가 없다. 가격은 주문 품목의 판매가뿐이다.

**판단 근거**
원천 주문은 product_id만 참조하므로, 상품당 SKU를 여러 개 만들면 원천 주문이 어느 SKU인지 알 수 없다.

**결정**
- 브랜드: 가상 생성 후 상품에 무작위 배정
- 상품명: 브랜드명 + 세부 카테고리 조합으로 생성
- SKU: 원천 상품당 기본 SKU 1개
- 정가: 해당 상품의 원천 판매가 중 최댓값 (할인 없는 가격으로 가정)

**가정·한계:** 상품명과 브랜드는 가상 값이며 README에 명시한다.

**영향 산출물:** 가상 데이터 생성, 매핑 정의서
